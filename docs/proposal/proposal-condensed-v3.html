Know before you merge whether you can roll back.

One-Way Door is a GitHub Copilot skill. On every pull request it answers the question no pipeline asks: if this goes wrong after deploy, can we actually roll back?
⇄ Two-way door: roll back any time→ One-way door: no way back
The problem

Rollback is every team's first response to a bad release, yet nobody checks that it works. When a release changes stored data or a message format, the old code may not run against what the release leaves behind. Teams find out mid-incident, and nothing before merge checks for it.

1sensible refactor: money from a double to whole pence. Tests green, review approved.
50settlements booked at £0.00 after the rollback. No exception, nothing in the dead-letter topic.
£12,708missing from the ledger, with every dashboard green. Finance's job broke first.
4small PRs instead, each one proven to roll back cleanly. Same end state.
The solution, in one folder
  • Classifies every change in a PR as two-way (safe to roll back) or one-way.
  • For each one-way change: when the door closes, what breaks on rollback, and the safe rollback window.
  • Finds the blast radius: other code that reads the same table, column, topic or field, even outside the PR.
  • Proposes a rollback-safe split (expand → migrate → contract → drop), and generates it on request.

VS Code, Copilot CLI, the cloud agent and code review. Offline: git and Node only.

Proven live, not mocked

An invented payments company, Northwind, runs three real Java services, Kafka and Postgres on one laptop. One PR is merged, rolled back, and books £0.00. The skill predicts each failure before merge, and its split passes a five-stage rollback test at every step.

The problem
Rollback is the safety net nobody tests

Code rolls back; state doesn't. A release that changes a table, an event or a stored format leaves data behind, and the previous version has to live with it. Nobody checks, before merge, that it can.

How a rollback goes wrong
Release N shipsit changes a schema, an event or a format
›
New state is writtentables migrated, events published, caches filled
›
An incidentrelated or not, the plan is to roll back
›
Roll back to N−1the code goes back; the state stays
›
Old code, new statefails, errors, or silently misreads
Four kinds of one-way change
Databases

Change: a column renamed, dropped or retyped; values converted in place.

Old code fails its schema check, or queries a column that's gone.

Events and messages

Change: a field removed, renamed or retyped; its units changed.

Old consumers read the missing field as zero or null, silently.

Caches and state

Change: a new serialisation format, new keys, rewritten idempotency records.

Old code can't read them: misses, errors, or work done twice.

External contracts

Change: webhooks in a new shape, API versions retired, topics deleted.

A redeploy can't take back what partners already received.

Why today's safeguards miss it: they all look forward
SafeguardWhat it checksWhat it never sees
Unit and integration testsnew code against a fresh databaseold code against data the new code wrote
CI/CD pipelinesdeploying forwarddeploying back after the state has changed
Migration toolsapplying changes in orderundoing them: most only go forward
Code reviewthe lines in the diffother services and jobs that read the same data
Monitoring and alertserrors and exceptionswrong values that raise no error
The worst failures are quiet: every dashboard green, every line £0.00.

Why it matters

  • Rollback fails just when it's needed most.
  • Recovery needs hand-written data fixes, under pressure.
  • Silent failures corrupt data for days before anyone notices.
  • Teams stop trusting rollback altogether.

What teams need, before merge

  • Is the change two-way or one-way?
  • When does the door close, and what breaks then?
  • Who else reads the data it changes?
  • How can it be split so each step can be undone?
Same goal, two kinds of door
GoalOne-way: in one releaseTwo-way: in steps
Rename a columnrename it in placeadd the new column, copy, switch readers, then drop

Replace an event fieldremove the old field, add the new onesend both; move every consumer; then stop the old

The system. The writer (settlement-service), the reader (ledger-service) and finance's job nobody remembered (reconciliation-batch). Real Java 21 services.
A double can't hold 0.10 exactly. Let's store whole pence, like the card schemes do.

Why PR #482 swaps double for long

0.1 + 0.2 == 0.30000000000000004 // before double amount = 268.47; // after long amountMinor = 26847;

Summed over millions of settlements, totals drift by pennies. A long in pence is exact. The idea is right; shipping it in one deploy isn't.

One PR, four changes at once (tests green, approved by Tom)

1Flyway V3 renames amount to amount_minor.

2It rewrites every row in pence: £268.47 → 26847.

3The event swaps amount for amountMinor.

4Not in the PR: finance's SUM(amount) job.

Why £0.00 and not an error

record PaymentSettled(…, double amount, …) ← missing: 0.0 // "amountMinor": 26847 → ignored

The old ledger reads by field name. Jackson ignores the unknown field; the missing double stays 0.0. Nothing throws, so nothing reaches the dead-letter topic.

What went wrong

Everyone watched the ledger. Nobody thought about settlement-service: it stayed on v2, and the events already on Kafka can't be rolled back. Nor about reconciliation-batch, which reads the table but isn't in the PR.

What's in the folder

  • SKILL.md: the instructions.
  • patterns.md: 24 one-way patterns, each with its safe split.
  • scan-migrations.mjs, schema-compat.mjs: offline checks, JSON out.
  • A path rule, a hook guarding shipped migrations, a plugin.

Where it runs

  • VS Code agent mode, before you push.
  • Copilot CLI, or /one-way-door.
  • Cloud agent on the PR on GitHub.
  • Code review, which can use repository skills.

Guardrails

  • Reviews only; never changes code unasked.
  • No servers, accounts or network calls.
  • The hook fails open: it never blocks your work.
  • Readers it can't see are assumed to exist.

The solution, proven
Same destination. Four deploys. Each one reversible.

The split ends exactly where PR #482 does, but keeps old and new side by side until nobody needs the old one. This time finance's job moves with the ledger.

1Expand

Table: add nullable amount_minor; write both.

Event: send both fields.

Finance: unchanged, SUM(amount).

⇄ old code ignores the new column

2Migrate

Table: backfill; check every row agrees.

Event: still both.

Finance: also flags any mismatch.

⇄ both columns correct

3Contract

Table: read only amount_minor; a trigger fills amount.

Event: still both; no amount goes to the DLT.

Finance: switches to SUM(amount_minor).

⇄ amount kept up to date

4Drop

Table: drop amount and the trigger.

Event: amountMinor only.

Finance: already moved in step 3.

⇄ nothing uses the old any more

The live demo, in five acts

A Java Control Centre starts real Postgres and Kafka, builds each service from git and runs it. The browser shows the PR, the incident, the review, the split and the proof. Every rollback runs the previous commit's code against today's data. Windows and macOS; a recorded run is the fallback.

Next: readers in other repositories

Search related repositories at their deployed versions, and assume any repository it can't reach reads the data. The verdict states its coverage, and the split names each repository's owner and order.

Every merge is a door. Know which kind before you walk through it.
