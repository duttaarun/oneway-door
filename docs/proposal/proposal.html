One way only ›
In one paragraph

Rollback is the safety net for every release, yet nothing checks that it works. A change is a one-way door when it leaves behind state the previous release can't handle: a migrated table, new-format messages, rule data in another repo, a payment already sent to SWIFT. One-Way Door is a GitHub Copilot skill that reviews each pull request for exactly this. It says whether rollback is safe and for how long, finds who else is affected, and proposes a safe sequence of smaller changes.

01 · The problem

Rollback is the safety net nobody tests

Problem statement

Engineers changing payment services can't tell, before merge, whether the previous release can run safely against the state the new release creates. When it can't, a routine rollback turns an incident into a bigger one: payments are processed wrongly without any error, and some reach SWIFT, where they can't be taken back.

Where one-way doors hide
Data

Columns renamed, dropped or converted in place. Migrations edited after they ran.

Messages

Fields removed, renamed or retyped. Consumers that read a missing number as zero.

Rule data

Keys or units change in one repo while the code that reads them lives in another.

External

Payments sent to SWIFT, partner webhooks, deleted queues. Redeploying can't recall them.

Why today's checks miss it
1
Tests run new code against new state.The combination that rollback creates, old code against new state, is never exercised.
2
Migration checks only see schemas.A change to rule data or a message contract has no migration to scan.
3
Reviewers see one repo.The code that reads a changed field often lives in another team's repo.
4
Controls fail open.A missing threshold means "skip the rule", not "stop the payment".

Why payments raise the stakes

  • SWIFT has no undo. Once sent, a payment can only be requested back through gpi Stop and Recall. After the money is credited, that needs the recipient's agreement.
  • Formats are changing now. MT payment instructions ended on 22 November 2025. Under CBPR+, fully unstructured addresses stop being accepted in November 2026 (14 November in bank guidance).
  • Estates are split across teams. Gateway, orchestrator, routing rules, outbound and data ingestion each have their own repo and release.
What a one-way door costs
SilentNo exception, nothing in the dead-letter queue, every dashboard green. Someone has to notice.
IrreversiblePayments at SWIFT can only be requested back. Converted or dropped data needs a restore.
Slow to unwindHand-written hotfixes, recall requests, incident reviews and explanations to risk and compliance.

Acceptance criteria
  1. Given a PR that renames or rescales rule data, when Copilot reviews it, then the verdict is ONE-WAY with a safe rollback window.
  2. Given a related repo that reads the changed key, then the review names the file and repo, and how many repos it checked.
  3. Given a ONE-WAY verdict, then the review proposes an expand, migrate, contract, drop split, and builds it only when asked.
  4. Given an agent editing a migration already on the default branch, then the edit is blocked with the reason.

03 · Proposed solution

A GitHub Copilot skill for the way back

One-Way Door is a GitHub Copilot agent skill: a folder of instructions, reference material and small scripts. Copilot loads it when someone asks to review a change, check release readiness, or asks "can we roll back?". It answers with one review comment, before merge.

What's in the box
.github/skills/one-way-door/
  SKILL.md · the procedure Copilot follows
  references/patterns.md · 24 one-way patterns
  references/output-format.md · the review format
  scripts/scan-migrations.mjs · risky DDL
  scripts/schema-compat.mjs · breaking events
.github/instructions/migrations…md · path rule
.github/hooks/one-way-door.json · pre-edit guard
plugins/one-way-door/ · one install, every repo

How a review runs
1
Diff from the merge base
2
Sort files: data, messages, state, external
3
Run the scripts: offline, JSON out
4
Find readers, here and in related repos
5
Judge old code against new state
6
Write the verdict, offer the split
The safe split
1 ExpandCode reads the new key, falls back to the old, holds if neither.
2 MigrateRule data carries both keys. The loader checks they agree.
3 ContractCode reads only the new key, and still fails closed.
4 DropRemove the old key once nothing reads it.
Design principles
Scripts check, Copilot judges
Offline: git and Node 20+
Controls fail closed
Plain verdicts, no guesswork
Says what it searched
Copilot's own formats

Hackathon build: across repos

A per-repo list of related repos, find-readers to search them, and data checks for renamed keys and values scaled ×10, ×100 or ×1000.

Hackathon scope
  • Must: Northwind repos (GTX, orchestrator, rules, outbound, ingestion), SWIFT and screening simulators, Spanner and BigQuery emulators, the story end to end, multi-repo skill support.
  • Stretch: the structured-address scenario, an approve endpoint for held payments, the recall flow.
Success measures (targets)
  • The review on PR #517 says ONE-WAY and names RuleEvaluator.java.
  • Cross-repo rollback tests: four steps pass, the bad change fails.
  • No TWO-WAY verdict on any change the tests show is unsafe.
Risks and limits
  • Spanner and BigQuery run as emulators, so behaviour can differ.
  • pacs.008 is a subset; no settlement or account posting.
  • Copilot decides to load a skill from its description. A manual checklist covers each surface.
  • Judgment can be wrong, so every review states what it searched and what it couldn't reach.
