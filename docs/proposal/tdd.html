01 · Problem statement

Rollback is the safety net nobody tests

Problem statement

Rollback is every team's first response to a bad release, yet nobody checks that it works. When a release changes stored data or a message format, the old code may not run against what the release leaves behind. Teams find out mid-incident, and nothing before merge checks for it.

How a rollback goes wrong
Release N shipsit changes a schema, an event or a format
›
New state is writtentables migrated, events published, caches filled
›
An incidentrelated or not, the plan is to roll back
›
Roll back to N−1the code goes back; the state stays
›
Old code, new statefails, errors, or silently misreads
Four kinds of one-way change
Databases

Change: a column renamed, dropped or retyped; values converted in place; a required column added.

Old code fails its schema check at start-up, or queries a column that's gone.

Events and messages

Change: a field removed, renamed or retyped; its units or meaning changed.

Old consumers read the missing field as zero or null, or drop the message.

Caches and stored state

Change: a new serialisation format, new keys, rewritten idempotency records.

Old code can't read the entries: misses, errors or work done twice.

External contracts

Change: webhooks sent in a new shape, API versions retired, queues or topics deleted.

A redeploy can't take back what partners have already received.

Why today's safeguards miss it: they all look forward
SafeguardWhat it checksWhat it never sees
Unit and integration testsnew code against a fresh databaseold code against data the new code wrote
CI/CD pipelinesdeploying forwarddeploying back after the state has changed
Migration toolsapplying changes in orderundoing them: most only go forward
Code reviewthe lines in the diffother services and jobs that read the same data
Monitoring and alertserrors and exceptionswrong values that raise no error

Why it matters

  • Rollback fails just when it's needed most.
  • Recovery needs hand-written data fixes, under pressure.
  • Silent failures corrupt data for days before anyone notices.
  • Teams stop trusting rollback altogether.

What teams need, before merge

  • Is the change two-way or one-way?
  • When does the door close, and what breaks then?
  • Who else reads the data it changes?
  • How can it be split so each step can be undone?

In scope: changes reviewed before merge in GitHub Copilot, and readers in the same repository. Out: other repositories (section 9), running rollbacks, live data, approving PRs. The demo shows it end to end (section 2.2).

02 · User story · 2.1

Know before you merge whether you can roll back

Primary user story

As a developer raising a pull request that changes a database migration or an event contract, I want GitHub Copilot to tell me before I merge whether the change can be rolled back, and if not, how to split it, so that a rollback never makes an incident worse.

Supporting stories

Priya

Backend developer · author of PR #482

As the author, I want a plain verdict and the reason, in my editor, so that I can fix the change before anyone reviews it.

Tom

Tech lead · reviewer

As a reviewer, I want every reader of a changed column or field, including ones outside the PR, so that I review the blast radius, not just the diff.

Sam

On-call engineer

As on-call, I want a safe rollback window for every release, so that I know whether pressing rollback will help or hurt.

Grace

Finance · owns the reconciliation

As the owner of a downstream job, I want changes to data I read to be flagged before merge, so that my totals never break or drift silently.

Acceptance criteria
  1. Given a PR with a destructive migration, when someone asks "can we roll back?", then the answer starts with Verdict: ONE-WAY and a safe rollback window.
  2. Then each finding says when the door closes, what breaks on rollback (quoting the real error when known), and what data is lost.
  3. Then the blast radius lists readers outside the PR, marked not in this PR.
  4. Then it proposes an expand → migrate → contract → drop split, justifies each step, and generates it only when asked.
  5. Given a safe change, then the verdict is TWO-WAY, window unlimited, with what was checked.
  6. Given no Node.js, then it still reviews from the catalogue and says the scripts didn't run.

02 · User story · 2.2

The demo story: a sensible refactor, then £0.00

The demo tells the user story end to end, with real code. Northwind Payments is an invented UK company that settles card payments for small merchants. One pull request, PR #482, gets merged without anyone asking whether it can be rolled back.

What the demo is

  • settlement-service, the writer: turns each settlement into a PaymentSettled event on Kafka.
  • ledger-service, the reader: books one row per event in Postgres ledger_entries.
  • reconciliation-batch, finance's job: sums that table directly. Nobody remembers it.
  • All three are real Java 21 services, built from git and run for real on one laptop.

Why PR #482 swaps double for long

  • A double can't hold most decimals exactly: 0.1 + 0.2 = 0.30000000000000004. Summed across millions of settlements, totals drift by pennies.
  • Card schemes send whole pence. A long is exact: amountMinor = 26847 is £268.47.
  • The idea is right. The trouble is shipping it in one deploy: Flyway V3 renames amount and rewrites every row in pence, and the event drops amount for amountMinor.

What went wrong

Everyone watched the ledger. Nobody thought about settlement-service: it stayed on v2 after the rollback, and the v2 events already on Kafka can't be rolled back. Nor about reconciliation-batch, which reads the table but isn't in the PR.

Mission

For every pull request, answer the question no pipeline asks: if this goes wrong after deploy, can we roll back? Say it plainly, before merge, inside the tools engineers already use, and show the safe way to make the same change.

What it does
1 · Classify

Every change is two-way (safe to roll back) or one-way (not safe).

2 · Explain

For each one-way change: when the door closes, what breaks on rollback, and a safe rollback window.

3 · Blast radius

Finds other code reading the same table, column, topic or field, and marks what isn't in the PR.

4 · Split

Proposes expand → migrate → contract → drop, and generates it as branches when asked.

How Copilot decides to load it: the description (its only trigger)
Rollback-safety review for pull requests, diffs and releases. Answers "if this goes wrong after deploy, can we roll back?" Use when reviewing a PR, checking deploy or release readiness, asking "is this safe to ship" or "can we roll back", or when a change touches database migrations (Flyway, Liquibase, EF Core), event or message schemas (Kafka, JSON Schema, Avro, Service Bus), serialised DTOs, caches, idempotency keys, partner webhooks or API versions. Classifies each change as one-way or two-way, says when the door closes and what breaks on rollback, gives a safe rollback window, finds other code that reads the same table, column or topic, and proposes an expand, migrate, contract, drop split it can generate as branches.

Design principles

Scripts check, Copilot judges

Scripts find the mechanical facts. Copilot judges who else reads the data and what old code does with it.

Copilot's own formats

Documented skill, instruction and hook formats. No custom runtime: every surface reads it.

Offline and dependency-free

git and Node's standard library. Nothing to install, call or keep running.

Load only what's needed

Description first; then the 167-line SKILL.md; references only when needed.

Plain, fixed verdicts

ONE-WAY or TWO-WAY, a window and reasons, in a fixed shape. Real errors, no hedging.

Safe by default

Never changes code unasked. Unreachable readers are assumed to exist.

The procedure (SKILL.md)
#StepWhat happens
1Work out base and headDefault branch from origin/HEAD; always diff from the merge base (base...head, three dots).
2Bucket the filesData, Messages, State or External, by path and content.
3Run both scriptsMechanical findings as JSON. Without Node, step 4 does the work alone.
4Read the patternsMatch each change to the catalogue, including buckets the scripts don't cover.
5Find the blast radiusSearch the whole repo (base and head) for every reader; mark those the PR doesn't change.
6Old code against new stateWhat does the previous release do with the new table, events or cache? Quote the real error.
7Write the commentThe verdict line, findings, blast radius and split, in the fixed format.
8Generate the splitOnly when asked: stacked branches, each commit saying why it rolls back.

scan-migrations.mjs

In: --base --head [--repo] [--worktree]. Reads: Flyway SQL, Liquibase (XML, YAML, formatted SQL), EF Core. Finds: column and table renames and drops, retypes, NOT NULL, in-place conversion, backfill, row deletes, edited applied migrations.

schema-compat.mjs

In: --base --head [--dir]… [--worktree]. Reads: JSON Schema (*.schema.json). Finds: fields removed, renamed, retyped or made optional, enum values added, new required fields, strict consumers, missing primitive defaults, deleted schemas.

Both: Node 20+ standard library, no network, read-only git; JSON findings[] (file, line, pattern, object, severity, detail); always exit 0.

05 · Setup instructions · 5.2

Setup by Copilot surface

VS Code (agent mode)

  1. VS Code 1.109+, signed in to Copilot; git and Node 20+ on the terminal's PATH.
  2. Open the folder that contains .github/; trust the workspace.
  3. Chat → Agent. Check chat.useHooks is on (default).
  4. Check: type / or /skills and look for one-way-door; /hooks for the hook; Developer: Open Agent Debug Logs if it's missing.
  5. Ask; approve the git and node commands. References should list SKILL.md.

Copilot CLI

  1. Install: npm i -g @github/copilot, winget install GitHub.Copilot or brew install --cask copilot-cli.
  2. Sign in with /login (or a fine-grained token with "Copilot Requests").
  3. Run copilot in the repo root and trust the folder.
  4. Check: /skills list shows one-way-door.
  5. Ask; approve the commands. A denied hook call shows inline with its reason.

Copilot cloud agent

  1. Paid plan. Org admin: policy "Copilot cloud agent" → Enabled (off by default), then Cloud agent → Repository access.
  2. Option A files on the default branch, including copilot-setup-steps.yml (job name copilot-setup-steps).
  3. Trigger: comment @copilot Review this PR for rollback safety, assign an issue, or use the agents panel.
  4. Check: the session log shows SKILL.md read and both scripts run. Firewall doesn't affect them: they are offline.

Copilot code review

  1. Paid plan. Org admin: policy "Copilot code review"; Actions runners available.
  2. Option A files on the PR's head branch: code review reads skills from there.
  3. One PR: Reviewers → Copilot. Every PR: a ruleset with "Automatically request Copilot code review".
  4. Expect the skill to be used "when relevant". Whether code review runs its scripts or hooks isn't documented; for a guaranteed full review, use the cloud agent.

Architecture: the demo system

Northwind Payments is invented. Three small Spring Boot services, one Kafka topic and one Postgres table: just enough to show a rollback that can't work.

Figure 1. The demo system, drawn in Lucidchart. Badges show the stack: Java 21, Spring Boot, Hibernate, Apache Kafka, PostgreSQL 16 and the React UI.

The writer

settlement-service takes POST /settlements and publishes PaymentSettled. v1 sends amount in pounds; PR #482 sends amountMinor in pence.

The reader

ledger-service consumes each event and books one row in ledger_entries. Flyway owns the schema; Hibernate validates it at start-up, so a wrong schema fails loudly.

The reader nobody remembered

reconciliation-batch runs finance's SUM(amount) straight from Postgres. It isn't in PR #482, so it breaks first. This is the blast radius.

Kept real on purposeWhy it matters to the story

08 · Reuse statements

Built for any repository, not just the demo

Reuse statement

One-Way Door is generic. Nothing in SKILL.md or its scripts refers to the demo; a test enforces that. Any team can reuse it in any GitHub repository by copying one folder or installing one plugin, with no servers, dependencies or changes to their build.

Clear statements
  1. Reusable as it is in any repository with Flyway, Liquibase or EF Core migrations, or JSON Schema event contracts.
  2. Language-agnostic. Blast radius uses git grep, so readers in Java, C#, Python, TypeScript or SQL are all found.
  3. Works without its scripts. Avro, Protobuf, caches, webhooks and APIs are reviewed from the catalogue.
  4. No infrastructure. git and, optionally, Node 20+. No packages, network or accounts beyond Copilot.
  1. Every Copilot surface from one copy: VS Code, CLI, cloud agent and code review.
  2. Optional parts are independent. Take the skill alone, or add the rule and the hook.
  3. MIT licensed. Copy, adapt and redistribute.
  4. The demo is reusable too as a pattern: build each version from git, mix old and new, check the money.

Readers across repositories (find-readers), rule-data checks, Spanner and BigQuery schemas.

Future scope: readers in other repositories

Today the skill finds readers with git grep in one repository. Real data is often read elsewhere: a finance job, a report, a partner adapter. Limitation 2 is the biggest gap, and this is the plan to close it.

What gets built
#ChangeWhat it does
1Related-repos config.github/one-way-door.json lists each related repo: GitHub name, local path if cloned, and the deployed ref, because the readers that matter are the ones running today. JSON, so the scripts stay standard-library Node.
2find-readers.mjsTakes the tables, columns, topics and fields the other scripts extract, with snake_case and camelCase variants, and searches each cloned repo at its deployed ref. Offline, deterministic, JSON out: per repo, searched or unreachable, the ref, and every hit.
3Copilot searches the restSKILL.md tells Copilot to use its own GitHub code search for repos that aren't cloned, where it has access. The scripts never call the network.
4Unreachable means a readerIf a related repo can't be searched, a change to shared data can't be TWO-WAY. The blast radius lists the repo as “unknown, assumed to read”, and the split keeps the old field until someone confirms.
5Coverage in the verdictOne line in output-format.md, for example: Searched 2 of 3 related repos at their deployed refs; partner-adapter unreachable, assumed to read.
6Cross-repo splitEach step names its repo, its owner (from CODEOWNERS) and its ordering rule: a reader's switch must be live before the drop ships. A new “split ownership” pattern in patterns.md.
7Tests and docsFixture tests with temporary repos: a reader in another repo, an unreachable repo, name variants, a deployed ref behind main. Then setup.md, the README and this page.

The safety rule: what it can't see, it assumes

Not knowing is treated as risk, never as all clear. It's the same principle as the hook. A skill that said TWO-WAY because it couldn't open finance's repository would be worse than no skill at all.

What each Copilot surface can reach

  • VS Code and Copilot CLI: related repos cloned side by side, or GitHub search when signed in.
  • Cloud agent and code review: the token usually reads only the current repo, so others show as unreachable, unless an org admin grants wider read access.

In the demo

Move reconciliation-batch into its own repository, northwind-finance. The verdict then reports “checked 2 of 2 related repos, SUM(amount) found in northwind-finance”. With that repo missing, it shows the cautious verdict. An earlier, larger multi-repo demo plan is in docs/multi-repo-plan.md.

10 · Guardrails

What it will and won't do

The skill: reviews, never acts on its own

  • Read-only by default. It never edits code, creates branches, pushes or opens pull requests unless the user asks (step 8).
  • No pre-approved tools: allowed-tools is deliberately not set, so every command it runs needs the user's approval.
  • States what it searched. Readers it can't check are assumed to exist, and it says so.
  • Quotes real errors; marks when scripts didn't run; no guesswork words, no hype, British English.

The scripts: deterministic and offline

  • Node standard library only; no packages, no network, no writes. They only read git.
  • Same input, same JSON output. Always exit 0: findings are data, not failures.
  • Always diff from the merge base, so other people's changes on main are never blamed on the PR.

The hook: a narrow guard that can't lock you out

  • Denies only one thing: agent edits to migrations already on the default branch, with a reason and the next version to use.
  • Reading, new migrations, repeatable and undo scripts and Liquibase changelogs stay allowed.
  • Fails open on its own errors: a broken hook must never block every tool call.

The path rule: rollback rules where they matter

  • Never rename, drop or retype a column in one step; never convert in place.
  • Never edit an applied migration: add a new one.
  • Event fields: add as optional; consumers move first; never let a missing number default to 0.

Platform controls respected

Workspace Trust, org and device policies, terminal approvals and the cloud agent's firewall all apply. The skill adds no way around them.

Data and privacy

No secrets or credentials needed. The scripts send nothing anywhere. Code is processed only by Copilot, under the user's existing licence.

Honest demo

Every rollback rebuilds the old code from git. Replay is labelled as a recording. All companies, people and amounts are invented.
